### Какие уязвимости обнаружены?

Уязвимости искались на exploit-db.com (и через `searchsploit` в Kali) по названию службы и версии из результатов сканирования.

1. **vsftpd 2.3.4: бэкдор (Backdoor Command Execution)**
   - Служба: FTP, порт 21/tcp, версия vsftpd 2.3.4.
   - CVE: CVE-2011-2523
   - Ссылка: https://www.exploit-db.com/exploits/17491
   - Суть: в архив vsftpd 2.3.4, который раздавался с официального сайта с 30 июня по 3 июля 2011 года, был встроен бэкдор. Если при входе указать в имени пользователя последовательность `:)`, сервер открывает командную оболочку на порту 6200/tcp. Результат: удалённое выполнение команд без аутентификации.

2. **Samba 3.0.20: выполнение команд через «username map script»**
   - Служба: SMB, порты 139/445, версия Samba 3.0.20-Debian.
   - CVE: CVE-2007-2447
   - Ссылка: https://www.exploit-db.com/exploits/16320
   - Суть: в версиях 3.0.20 – 3.0.25rc3 при включённой опции `username map script` имя пользователя передаётся в `/bin/sh` без экранирования. Имя со спецсимволами shell позволяет выполнить произвольные команды. Сопоставление имён происходит до аутентификации, поэтому учётная запись не нужна.

3. **distccd: удалённое выполнение команд (DistCC Daemon Command Execution)**
   - Служба: distccd, порт 3632/tcp, distccd v1.
   - CVE: CVE-2004-2687
   - Ссылка: https://www.exploit-db.com/exploits/9915
   - Суть: демон распределённой компиляции принимает задания от любого клиента и не ограничивает, какие команды выполнять. Атакующий передаёт вместо задания на компиляцию произвольную команду, и она выполняется с правами пользователя службы. Уязвимы distccd 3.1 и более ранние версии; причина — слабая конфигурация службы.

## Задание 2

### Методика

Для TCP-сканов взяты порты 21, 22, 80 (по заданию 1 они открыты) и 9999 (закрыт), для UDP-скана — 53, 111, 137 (открыты) и 9999 (закрыт). Так в каждой записи видны ответы и открытого, и закрытого порта.

Каждый скан записан в Wireshark отдельно, с фильтром захвата `host 192.168.139.128`. Файлы записей лежат в папке [pcap](pcap/): [syn.pcapng](pcap/syn.pcapng), [fin.pcapng](pcap/fin.pcapng), [xmas.pcapng](pcap/xmas.pcapng), [udp.pcapng](pcap/udp.pcapng).

```
sudo nmap -sS -n -Pn --reason -p 21,22,80,9999 192.168.139.128
sudo nmap -sF -n -Pn --reason -p 21,22,80,9999 192.168.139.128
sudo nmap -sX -n -Pn --reason -p 21,22,80,9999 192.168.139.128
sudo nmap -sU -n -Pn --reason -p 53,111,137,9999 192.168.139.128
```

`-Pn` отключает предварительное обнаружение хоста, чтобы в записи остался только сам скан. `--reason` выводит, по какому ответу nmap определил состояние порта. ARP-запрос и ответ в начале каждой записи — это определение MAC-адреса на канальном уровне, частью скана они не являются.

Результаты nmap:

| Режим | 21/22/80 | 9999 | Время скана |
|---|---|---|---|
| SYN | open (`syn-ack`) | closed (`reset`) | 0,14 с |
| FIN | open\|filtered (`no-response`) | closed (`reset`) | 1,32 с |
| Xmas | open\|filtered (`no-response`) | closed (`reset`) | 1,33 с |
| UDP (порты 53/111/137) | open (`udp-response`) | closed (`port-unreach`) | 0,16 с |

### SYN-сканирование (`-sS`)

**Трафик.** Kali отправляет на каждый порт TCP-сегмент только с флагом SYN, то есть первый шаг трёхэтапного рукопожатия. Nmap собирает пакет сам через raw-сокет, это видно по нетипичным параметрам: `Win=1024` и единственная опция MSS.

**Ответ сервера:**

- открытый порт (21, 22, 80) отвечает **SYN, ACK**. Kali в ответ отправляет **RST**, и рукопожатие обрывается на втором шаге. Соединение не устанавливается, поэтому режим называют полуоткрытым (half-open). RST отправляет ядро Kali: оно не знает о SYN, который nmap собрал вручную, и сбрасывает неожиданный SYN/ACK;
- закрытый порт (9999) отвечает **RST, ACK**.

На каждый порт уходит один пакет и приходит один ответ. Это самый быстрый режим, и он однозначно различает открытые и закрытые порты.

### FIN-сканирование (`-sF`)

**Трафик.** Kali отправляет сегменты только с флагом FIN («завершение соединения»), хотя соединения не было.

**Ответ сервера:**

- закрытый порт отвечает **RST, ACK**. `Ack=2` означает, что сервер подтвердил получение FIN;
- открытый порт **не отвечает**. По RFC 793 сегмент без флагов SYN, RST и ACK, пришедший на порт в состоянии LISTEN, молча отбрасывается.

Не получив ответа, nmap примерно через секунду повторяет FIN с нового порта-источника. Ответа снова нет, и порт помечается как `open|filtered`: по одной тишине нельзя отличить открытый порт от порта за файрволом, который отбрасывает пакеты. Из-за ожидания и повторов скан идёт заметно дольше SYN (1,32 с против 0,14 с).

### Xmas-сканирование (`-sX`)

**Трафик.** Kali отправляет сегменты с тремя флагами сразу: FIN, PSH и URG. Режим назван так потому, что флаги «горят, как гирлянда на ёлке». Указатель срочных данных при этом равен нулю (`Urg=0`).

**Ответ сервера** такой же, как при FIN-скане: закрытый порт отвечает **RST, ACK**, открытый молчит, после повторного запроса nmap ставит `open|filtered`.

От FIN-скана Xmas отличается только набором флагов, логика ответа сервера та же (RFC 793). Такая комбинация флагов не встречается в нормальном трафике, поэтому системы обнаружения вторжений легко распознают Xmas-скан как аномалию.

FIN- и Xmas-сканирование работают только против систем, которые строго следуют RFC 793, например Linux (Metasploitable). Windows отвечает RST на такие сегменты независимо от состояния порта, поэтому против неё оба режима покажут все порты закрытыми.

### UDP-сканирование (`-sU`)

**Трафик.** В UDP нет рукопожатия и флагов, nmap просто отправляет датаграммы. Многие UDP-службы не отвечают на пустой пакет, поэтому на известные порты nmap шлёт настоящий запрос нужного протокола:

- на 111: RPC-вызов Portmap;
- на 137: NetBIOS-запрос NBSTAT;
- на 53: DNS-запросы, в том числе `version.bind`;
- на 9999: пустая датаграмма (`Len=0`).

**Ответ сервера:**

- открытый порт отвечает данными на уровне приложения: Portmap Reply, NBSTAT response, DNS response. Nmap ставит `open` (`udp-response`);
- закрытый порт: отвечает не приложение, а ядро ОС — сообщением **ICMP Destination unreachable, Type 3, Code 3 (Port unreachable)**. Внутри сообщения лежит заголовок исходной датаграммы. Nmap ставит `closed` (`port-unreach`);
- если ответа нет совсем, nmap ставит `open|filtered`. В этом скане такого не было: все открытые службы ответили на свои запросы.

**Дополнительные наблюдения.** В записи есть ICMP Port unreachable, которые отправил сам Kali в ответ на UDP-ответы сервера. Это аналог RST при SYN-скане: ядро Kali не знает о датаграммах, отправленных nmap через raw-сокет. После шести таких сообщений Kali перестал их отправлять. Так работает ограничение частоты ICMP-ошибок в Linux. Тот же механизм на стороне цели сильно замедляет UDP-сканирование большого числа закрытых портов: Linux отправляет ICMP Port unreachable примерно раз в секунду.

### Итог: чем отличаются режимы

| Режим | Что отправляет сканер | Открытый порт | Закрытый порт | Нет ответа |
|---|---|---|---|---|
| SYN | TCP с флагом SYN | SYN, ACK (сканер отвечает RST) | RST, ACK | filtered |
| FIN | TCP с флагом FIN | нет ответа | RST, ACK | open\|filtered |
| Xmas | TCP с флагами FIN, PSH, URG | нет ответа | RST, ACK | open\|filtered |
| UDP | UDP-датаграмма (с запросом протокола или пустая) | ответ службы | ICMP Type 3 Code 3 | open\|filtered |

Режимы различаются тем, что именно отправляется в сеть: флаги TCP-сегмента или протокол. Отсюда разное поведение сервера. При SYN-скане открытый порт сам подтверждает, что открыт. При FIN- и Xmas-сканах открытый порт молчит, а отвечает только закрытый. При UDP-скане открытый порт отвечает данными приложения, а закрытый — сообщением ICMP от ядра ОС.
